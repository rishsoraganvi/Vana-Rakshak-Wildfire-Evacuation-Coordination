<objective>
Build versioned, immutable plan persistence for PLAN-08. It has three parts:
- a `PlanningRepository` interface with a SQL implementation and an in-memory implementation
- advisory-locked version assignment with parent link, diff, supersede and an optimistic `state_version` check
- the in-transaction capacity re-check and shared-state snapshots

It also adds the material-change signature (D-16) and records the persistence architecture in ADR-002.

Purpose: "A material route/shelter change creates a new version" and "plans are immutable, versioned, provenance-linked" are exit criteria. RESEARCH found the current `MAX(version)+1` read races, and found that offline tests break on any new SQL in graph nodes.
Output: `coordinator/repository.py`, `planning/diff.py`, an extended `SharedState`, offline tests, a live integration test, and ADR-002.
</objective>

`SqlPlanningRepository(engine)` implements the protocol with `text()` and named parameters. `shelters()` delegates to `agent_shelter.registry.fetch_shelters`. `edge_statuses()` delegates to `wildfire_core.db.repositories.current_edge_statuses`. `weather_for()` delegates to `agent_weather.agent.get_weather_snapshot`. `flush_audit()` runs `flush_audit_entries` inside `engine.begin()`.

`persist_plan` runs in one `engine.begin()` transaction, in this order:
(1) `SELECT pg_advisory_xact_lock(hashtext(CAST(:incident_id AS text)))`
(2) `SELECT state_version FROM incidents WHERE id = :incident_id FOR UPDATE`. If it differs from expected, raise StateVersionConflict before any write.
(3) For a pending_review plan with assignments, `SELECT id, capacity, usable_factor, occupancy, is_active FROM shelters WHERE id IN :ids FOR SHARE` with an expanding bindparam. Compute available with `agent_shelter.registry.usable_capacity` minus occupancy. If any shelter sum exceeds available, or a shelter is inactive, raise CapacityRecheckFailed with readable messages (Rules 6).
(4) `SELECT COALESCE(MAX(version), 0) + 1` for the incident
(5) Build `final = plan.model_copy(update={"version": v, "parent_plan_id": parent_plan_id})`, then INSERT into plan_versions: id, incident_id, version, status cast as plan_status, rationale_md, is_llm_fallback, is_simulated, warnings, plan_data (final dumped with sort_keys), parent_plan_id, trigger_id, state_version (the expected value), plan_schema_version, validation (JSON list), freshness, provenance, diff, used_fallback and valid_until. JSON values go through `CAST(:x AS jsonb)`.
(6) `UPDATE plan_versions SET status = 'superseded' WHERE incident_id = :incident_id AND id <> :new_id AND status IN ('draft', 'pending_review', 'failed') RETURNING id`
(7) `UPDATE incidents SET state_version = state_version + 1, status = CAST(:incident_status AS incident_status) WHERE id = :incident_id RETURNING state_version`. The incident status is 'awaiting_review' for a pending_review plan and 'planning' for a failed one.
(8) INSERT into shared_state_snapshots with (incident_id, new state_version, the SharedState JSON from Task 3, or for this task a minimal one with references).

`InMemoryPlanningRepository` implements the same semantics with dicts: incidents, hotspots, triggers, weather points, settlements, shelters, edge statuses, plans and audit entries. Give it constructor or helper methods for test seeding: `add_incident`, `add_hotspots`, `add_weather_point`, `add_settlement`, `add_shelter`, `set_edge_status` and `update_occupancy`. It is production code, usable for replay or offline demos, and plans 03-10 and 03-11 import it.

`test_repository.py`:

- A changed state_version raises StateVersionConflict with no INSERT issued.
- An occupancy re-check overflow raises CapacityRecheckFailed with no INSERT.
- InMemory: two persists give versions 1 and 2, v2.parent == v1, v1 status superseded, and state_version increments by 1 per persist.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| coordinator → Postgres | Plans, versions and shared state are written by the app role |
| concurrent coordinator runs → same incident | Re-plans and replays may race |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-08-01 | Tampering | Concurrent persists racing on the version number | high | mitigate | `pg_advisory_xact_lock(hashtext(incident))` plus the unique (incident_id, version) constraint, in one transaction |
| T-03-08-02 | Tampering | Plan built on stale shared state overwriting newer state | medium | mitigate | `state_version` FOR UPDATE check raises StateVersionConflict before writes |
| T-03-08-03 | Tampering | Capacity changed between planning and persist (overbooking) | high | mitigate | FOR SHARE re-check of occupancy and usable capacity in the persist transaction raises CapacityRecheckFailed. The caller persists a failed plan (plan 03-10). |
| T-03-08-04 | Tampering | Silent mutation of a stored plan | high | mitigate | DB trigger (plan 03-04) proven live here. Frozen app models. Only status updates are issued. |
| T-03-08-05 | Repudiation | A re-plan silently replacing the current plan | medium | mitigate | parent_plan_id, diff jsonb and superseded status keep the full chain (D-16) |
| T-03-08-06 | Tampering | SQL injection through ids | low | mitigate | Parameterised binds, uuid typing, and expanding bindparam for IN lists |
</threat_model>
